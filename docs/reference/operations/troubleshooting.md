# Operational Troubleshooting

This page collects the failure modes you are most likely to hit while deploying and running Sayabot, with the exact code paths that produce each error so you can verify the cause in your own logs. It synthesizes behavior from the deploy scripts, the orchestrator, `computerd`, egress, and the database layer; setup walkthroughs live in [deployment.md](deployment.md) and the top-level [self-hosting guide](../../self-hosting.md).

Source files: `deploy/deploy.sh`, `packages/db/src/migrate.ts`, `packages/db/src/client.ts`, `packages/llm/src/crypto.ts`, `apps/orchestrator/src/db.ts`, `apps/orchestrator/src/ssrf.ts`, `apps/orchestrator/src/jobs/webhook.ts`, `apps/orchestrator/src/realtime.ts`, `apps/computerd/src/backends/select.ts`, `apps/egress/src/index.ts`, `packages/db/sql/0003_realtime.sql`

## 🗃️ Migration Ordering and Failures

**Symptom**: `deploy.sh migrate` fails with "relation does not exist" or the deploy aborts before rollout.

**What actually happens**: migrations run in the one-off `migrate` compose container (`deploy/docker-compose.yml:104-115`, command `node --import tsx src/migrate.ts` in `/app/packages/db`). The engine (`packages/db/src/migrate.ts:17-32`) first applies the Drizzle snapshot folder, then every **sorted** `.sql` file in `packages/db/sql/`. Two consequences:

- Bundled Supabase must create its own schemas (`auth`, `storage`, `_realtime`) **before** Sayabot migrates. `deploy.sh start_supabase` (deploy.sh:272-277) starts the five Supabase services and waits for health first, and the compose overlay gives `migrate` `depends_on` conditions on all of them (docker-compose.supabase.yml:210-219). If migrations fail with missing Supabase objects, check `./deploy/deploy.sh logs supabase-db supabase-auth` — the running release is untouched ("Migrations failed. Nothing was rolled out", deploy.sh:296-299).
- The `packages/db/sql/*.sql` files are re-executed on every migrate run (they are not tracked in a migration table), which is why each is written idempotently with `if not exists` guards — e.g. `packages/db/sql/0003_realtime.sql:11-17` checks `pg_publication_tables` before re-adding tables. If you add a raw SQL file it must tolerate being run twice.

**Hosted Supabase port trap**: preflight rejects `DATABASE_URL` URLs containing `:6543/` ("Use the session pooler (5432)", deploy.sh:106) because the transaction pooler does not support the session-level behavior migrations and advisory locks need.

## 🔑 KEK Mismatches and Bad Keys

**Symptom**: saved API keys, connector tokens, or webhook secrets become unreadable; logs show decryption failures like "stored webhook secret is unreadable" (`apps/orchestrator/src/jobs/webhook.ts:58-62`).

**Cause**: every secret is AES-256-GCM sealed with `SAYABOT_KEK` (legacy `MESH_KEK`). `parseKek` (`packages/llm/src/crypto.ts:10-16`) throws "SAYABOT_KEK (or MESH_KEK) must decode to exactly 32 bytes (generate with: openssl rand -base64 32)" if the value is missing, not base64, or not 32 bytes after decode. Because GCM authentication is all-or-nothing, a wrong-but-valid KEK never produces a partially correct plaintext — it throws on `decipher.final()`.

**Fix**: the KEK is generated by `deploy/install.sh` (install.sh:195-196) and deliberately preserved on re-run; there is **no recovery** for data sealed with a lost key — reset the affected credentials and re-enter them. Preflight requires a non-empty `SAYABOT_KEK` (deploy.sh:93-95). Keep `.env.production` backed up alongside database dumps (`deploy.sh backup` prints this reminder, deploy.sh:288).

## 🔒 Advisory Lock Stalls

**Symptom**: turns for one room execute slowly or appear serialized behind a stuck run; other rooms are unaffected.

**What actually happens**: `withRoomLock` (`apps/orchestrator/src/db.ts:29-42`) takes a **session-level** `pg_advisory_lock(hashtext('mesh:room:<roomId>'))` on a **dedicated** client from the pool and only unlocks/releases in nested `finally` blocks. The whole turn runs inside it (`apps/orchestrator/src/coordinator/index.ts:345`), so a hung agent loop or a held connection blocks the next turn for that room indefinitely — `pg_advisory_lock` waits, it does not time out. `pg_blocking_pids()` on the locked room key identifies the holder.

**Failure modes to check**:

- Someone bypassed the pattern: advisory locks are connection-scoped, so calling them through `pool.query(...)` can acquire and release on **different physical connections**, leaking a lock forever (the reason the dedicated-client pattern exists, db.ts:25-28).
- A crash between lock and unlock (e.g. `kill -9`) — Postgres releases session locks at disconnect, but a zombie connection keeps it; restart the orchestrator or terminate the backend PID.
- One human message supersedes in-flight work via LISTEN/NOTIFY interrupt (coordinator/index.ts:341-342), but bot-triggered wakeups deliberately queue behind the current session — that is by design, not a stall.

## 🏊 Pooler Connection Limits

**Symptom**: `timeout exceeded when trying to connect` or `sorry, too many clients already` from Postgres.

**Cause**: each process opens its own pool via `createDb` (`packages/db/src/client.ts:5-19`): `max` defaults to **4** when `DATABASE_URL` contains `.pooler.supabase.com` (Supabase's per-client pooler slots are tight) and **10** otherwise, overridable with `DATABASE_POOL_MAX`. Idle timeout is 10s, connection timeout 10s. Both `web` and `orchestrator` plus every `deploy.sh migrate`/`seed` one-off container create pools, and `withRoomLock` pins one extra connection per active turn.

**Fix**: lower `DATABASE_POOL_MAX`, and keep migrations on the session pool (port 5432). Note the bundled stack connects directly to `supabase-db:5432` with no pooler, so this applies mainly to hosted Supabase.

## 🖥️ computerd Backend Selection Failures

**Symptom**: log line `[computerd] no computer backend available (...) ; defaulting to docker` or computer start failures like "No such image".

**What actually happens**: `selectBackend` (`apps/computerd/src/backends/select.ts:71-95`) tries, in order, smolvm → docker → e2b, collecting reasons: smolvm fails with "no hardware virtualization (needs /dev/kvm or Apple silicon)", "smolvm not installed (...)", or a failing `smolvm --version` (`apps/computerd/src/backends/smolvm.ts:342-356`); docker fails with "daemon not reachable" (no `/var/run/docker.sock` or group membership); e2b throws `BackendUnavailableError("E2B_API_KEY is not set")` (select.ts:54). If everything fails it **falls back to docker**, which then fails per-computer.

**Common concrete causes**:

- The computer image was never built: compose never builds `saaya/computer:<tag>`; `deploy.sh build_computer_image` does — "Without this step every computer fails with 'No such image'" (deploy.sh:256-258). It also `docker save`-exports the image for smolvm hosts (deploy.sh:263-268).
- smolvm mode without the overlay: `docker-compose.smolvm.yml` (giving computerd `/dev/kvm` and `/opt/smolvm`) is only added when `COMPUTER_BACKEND=smolvm` is set and `setup-computers.sh` ran.
- Explicit `smolvm` on a non-KVM host: `setup-computers.sh` dies with "No /dev/kvm..." and smolvm startups throw `smolvm is not runnable: ...` (smolvm.ts:123).

## 🌐 Egress Blocks (SSRF Guard)

**Symptom**: `403 saaya: forbidden host (...)` responses through the egress proxy, or `[egress] SSRF blocked: ...` warnings in egress logs (`apps/egress/src/index.ts:155-162`).

**What is blocked**: `assertSafeEgressHost` (`packages/core/src/server/ssrf.ts:158-195`) rejects local/internal suffixes (`localhost`, `.localhost`, `.local`, `.internal`, `.onion`), any private/reserved IP — loopback, RFC1918 (10/8, 172.16/12, 192.168/16), link-local and cloud metadata (169.254/16), CGNAT 100.64/10, TEST-NETs, multicast/reserved — and unparseable IPv6, checking **all** DNS results and then pinning the resolved IP for the upstream request to defeat TOCTOU DNS rebinding (`apps/egress/src/index.ts:155-170`). `isPrivateIp` also catches IPv4-mapped IPv6 (`::ffff:10.0.0.5`) and NAT64/6to4-embedded IPv4 (ssrf.ts:116-138).

**Related traps**:

- Webhook delivery has its own guard, `assertSafeWebhookUrl` (`apps/orchestrator/src/ssrf.ts:10-45`): rejects credentials-in-URL, non-HTTP(S) schemes, and private hosts; re-checks DNS on every attempt. Localhost bots need `SAYABOT_ALLOW_PRIVATE_WEBHOOKS=true` on the orchestrator (documented in the example README and plumbed at deploy/docker-compose.yml:92).
- Bot containers reach the internet only through egress on the `internal: true` `botnet` network (deploy/docker-compose.yml:214-217); if a computer has no connectivity, verify egress is on both networks and `EGRESS_PROXY_URL` points at `http://egress:8080`.
- Invalid per-agent proxy credentials get `407 saaya: invalid proxy credential`, and spoofed `x-saaya-agent-id` headers get `403 saaya: agent identity mismatch` (egress/index.ts:139-152).

## ✍️ Webhook Signature Failures

**Symptom**: your external bot answers `401 invalid signature`; orchestrator logs show non-2xx deliveries in `webhook_deliveries`.

**Signing side**: `deliverWebhook` (`apps/orchestrator/src/jobs/webhook.ts:75-90`) sends `webhook-id` (`msg_<uuid>`), `webhook-timestamp` (unix seconds), and `webhook-signature` produced by `signWebhook` from `@sayabot/core/server` — HMAC-SHA256 over `{webhook-id}.{webhook-timestamp}.{body}` with the base64-decoded secret. Delivery has a 15s timeout and throws on non-2xx so pg-boss retries with backoff (webhook.ts:92-110).

**Verification side** (reference bot, `examples/python-bot/bot.py:42-68`): reject when headers are missing; reject timestamps older than **300 seconds** (`TOLERANCE_SECONDS`); compare `v1,<base64>` parts with `hmac.compare_digest`.

**Usual causes, in order of frequency**: the secret was not base64-decoded before HMAC (strip the `whsec_` prefix first, bot.py:35-39); a proxy mutated the raw body (sign the exact bytes received); clock skew beyond the 5-minute window; or the secret was regenerated in the UI but not updated in the bot. Note the stored secret is sealed with the KEK — after a KEK change every delivery logs "stored webhook secret is unreadable" (webhook.ts:58-62).

## 📺 SSE / NDJSON Buffered by a Proxy

**Symptom**: streaming replies arrive in one burst at the end (or not at all), while non-streaming requests work.

**Where buffering is explicitly disabled** — all four layers must agree:

1. nginx `/collab` WebSocket: `proxy_buffering off` with 1h timeouts (deploy/nginx/snippets/sayabot-locations.conf:6-12).
2. nginx `/api/v1` + `/mcp`: `proxy_buffering off`, `proxy_request_buffering off`, `proxy_cache off`, `X-Accel-Buffering: no`, 330s timeouts (sayabot-locations.conf:16-27).
3. The Next.js proxy route sets `x-accel-buffering: no` on streaming responses (`apps/web/src/app/api/v1/[...path]/route.ts:361-362`) and passes streaming bodies through with `duplex: "half"`.
4. In tunnel mode, the same locations serve through cloudflared — Cloudflare's edge may still buffer; `X-Accel-Buffering: no` is respected, but long responses also have to fit the route timeouts.

If you put Sayabot behind your own proxy instead, replicate `proxy_buffering off` + `X-Accel-Buffering no` and keep read timeouts above 300s, or nginx's 60s default (`deploy/nginx/nginx.conf:48`) will cut streams. Rate-limit zones return **429** (`limit_req_status 429`, nginx.conf:75), so sudden 429 bursts on `/api/v1` are the `sayabot_api` zone (20 r/s, burst 60) not an app error.

## 📡 Realtime Auth Failures

**Symptom**: rooms load but live updates (messages, approvals, canvas) don't arrive; browser console shows channel errors; orchestrator logs `[realtime] broadcast ... failed: <status> <body>`.

**How it is wired**: the orchestrator broadcasts over Supabase Realtime's **REST** API with the service-role key (`apps/orchestrator/src/realtime.ts:12-28`, topic `room:<roomId>`, `private: true`); browsers join the same topic with WebSocket and must call `supabase.realtime.setAuth(session.access_token)` on every session refresh (`apps/web/src/components/room/use-room-realtime.ts:254-255`).

**Causes and fixes**:

- **Private channel authorization**: private broadcast/presence channels are authorized by RLS on `realtime.messages` (`packages/db/sql/0003_realtime.sql:24-56`): the JWT's user must pass `public.can_read_room(room.id)` for topic `room:<uuid>`. An expired/anonymous token, or a user outside the room's org, is rejected. Guests (anonymous sign-ins) need `GOTRUE_EXTERNAL_ANONYMOUS_USERS_ENABLED=true` in bundled mode, or "Allow anonymous sign-ins" on hosted Supabase.
- **Missing publication**: `messages`, `tool_calls`, `canvases` are added to the `supabase_realtime` publication idempotently by the same migration (0003_realtime.sql:4-20) — it silently does nothing if the publication doesn't exist, so a non-Supabase Postgres (no publication) yields no `postgres_changes` events.
- **Shared JWT secret**: all bundled services sign/verify with the same `JWT_SECRET` (docker-compose.supabase.yml:81,130,163-165); a mismatch between GoTrue and realtime/PostgREST produces valid-login-but-no-live-data symptoms. Regenerate via `deploy/install.sh`, never by hand-editing one service.
- **Tunnel/gateway**: nginx sets `Host: realtime-dev.supabase-realtime` on `/realtime/v1/` because realtime picks its tenant from the Host header (`deploy/nginx/supabase-locations.conf:48-59`); stripping or rewriting this header breaks the socket. The tenant admin API paths (`/realtime/v1/api/tenants`, `/openapi`) intentionally return 403.

## 🧰 Quick Diagnostic Commands

```bash
./deploy/deploy.sh status                 # compose ps + current release
./deploy/deploy.sh logs orchestrator web  # last 200 lines, follow
./deploy/deploy.sh releases               # release history (.releases)
docker logs <computerd container>         # backend selection + per-computer lifecycle
curl -fsSk --resolve "$DOMAIN:443:127.0.0.1" "https://$DOMAIN/api/health"
```

For locked rooms, `select pg_blocking_pids(<pid>)` and `select * from pg_locks where locktype = 'advisory';` identify the holder; for egress rejections, the `[egress] SSRF blocked:` warning names the exact rule.
